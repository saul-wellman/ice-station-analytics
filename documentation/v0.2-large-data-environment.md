# Ice Station v0.2 — Large Training Database

The original `ice_station` database is a small v0.1 onboarding sample and is retained. The larger working environment is created separately as `ice_station_v2`.

## Dataset targets

| Table | Target rows | Description |
|---|---:|---|
| customers | 25,000 | Synthetic customer profiles across Indian cities |
| products | 1,000 | Product catalogue across ten categories |
| stores | 30 | Fictional stores across Indian regions |
| orders | 100,000 | Order headers from 2023 through setup date |
| order_items | 250,000 | One to four item lines per order |
| payments | 100,000 | One synthetic payment event per order |
| returns | Variable | Item-level rows for returned orders |
| inventory_movements | Variable | Opening stock, store sales, returns, purchases and adjustments |

All data is synthetic. It must not be represented as real company/client data.

## Build from the repository (Windows + Git Bash)

1. Fetch the committed release: `git pull origin main`.
2. From the repository root run: `bash scripts/setup_large_dataset.sh`.
3. Enter the local PostgreSQL `postgres` user's password when prompted.
4. The script creates `ice_station_v2`, runs the committed SQL files, and validates the row counts. It refuses to overwrite a database and leaves `ice_station` unchanged.

The script expects PostgreSQL 18 command-line tools at `/c/Program Files/PostgreSQL/18/bin`, matching the initial setup. If your installation path differs, set `PG_BIN` to your PostgreSQL `bin` directory before running.

## Why generated rows are not committed to GitHub

GitHub stores the schema, generator SQL, setup automation and documentation. PostgreSQL generates and stores the large rows locally. This keeps the repository small while allowing the training database to be recreated from version-controlled code.

## Controlled training issues

Most order headers match the item-level totals. A small, documented subset is then adjusted by INR 100 to simulate source-system reconciliation problems. A small share of customer state values use variants such as `MP` and `M.P.` for future standardisation exercises. The build script validates expected row counts and item arithmetic.

## Safety

Run the build only for a new database. It does not overwrite existing databases. Use separately reviewed migrations for future schema changes.
